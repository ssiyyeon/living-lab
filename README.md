# 당직 근무자를 위한 문서 기반 민원 검색 플랫폼 (유성구청 리빙랩)

> 이 README는 공식 **요구사항 명세서**를 기준으로 전면 개정되었습니다. 이전 버전은 "민원내용 → 담당부서 분류 모델"을 목표로 진행했지만, 명세서 확인 결과 이 프로젝트의 정체는 **분류/예측 시스템이 아니라 문서 기반 검색·근거 제공 플랫폼**입니다. 아래 0~1절에 그 차이를 정리하고, 3절부터 새 커리큘럼을 제시합니다.

## 프로젝트 목표 3단계 (진행 현황 요약)

전체 계획은 아래 3단계 순서로 진행합니다. 각 단계의 현재 완성도를 솔직하게 적어둡니다.

### 1단계 — 매뉴얼을 코드화해서, 검색하면 관련 안내가 뜨게 한다

- **완성도: PDF 85페이지 전체 코드화 완료 (28개 케이스 + 8개 일반문서)**
- PDF의 "상황→대응→부서→연락처" 형식으로 된 케이스 28개(민원처리 19개 + 재난유형별 9개)는 검색어를 넣으면 해당 매뉴얼이 뜨도록 완료(`manual/situations.json` + `manual/rule_lookup.py`)
- 케이스 형식이 아닌 나머지 8개 섹션(당직근무자 준수사항, 청사보안, 비상연락망, 재난보고 개요, 당직일지 작성법, 소화기 비치 등)도 추가 코드화 완료(`manual/general_docs.json` + `manual/general_lookup.py`), 검색 시 `근거수준: "일반매뉴얼"`로 구분 제공
- `search/engine.py`가 매뉴얼(28개 케이스) → 일반매뉴얼(8개 문서) → 참고사례 → 근거불충분/결과없음 순으로 판정

### 2단계 — 전체 내용 표시 + 디테일한 입력엔 디테일한 안내 (예외는 담당 부서 직접 문의)

- **완성도: "전체 내용 표시" 100%, "디테일 분기" 28개 중 실제로 분기가 있는 10개 전부 완료**
- 검색 결과에 매뉴얼 원문을 요약 없이 전체 다 보여주는 건 완료
- 하나의 매뉴얼 항목 안에 여러 세부 케이스가 섞여있을 때 되물어서 좁혀주는 기능(`search/followup.py`)을 10개 항목에 구현:
  불법주정차, 포트홀·싱크홀·신호등, 유기동물, 가로수 전도, 도로상 낙하물, 소음 민원, 가스폭발, 산불, 화재발생, 하천 기름유출
- 나머지 18개는 검토 결과 원래 단일 절차(분기 없음)이거나, 동별 조회표·외부기관 연락흐름도라 "선택지 되묻기"보다 전체 원문 표시가 더 적합하다고 판단해 그대로 둠(재활용 수거요일표, 이동식 차수판 대여 문의처, 건축물 붕괴 연락체계도 등)
- 예외(선택지 어디에도 안 맞는 경우) → "담당 부서에 직접 문의하세요" 안내는 완료, 모든 역질문에 공통 적용됨
- **실사용 데이터 정합성 점검 중 발견·수정한 버그 4건**:
  1. 초기 세션에서 수작업으로 만든 `situations.json`의 "담당자" 필드에 붙임 참고자료 표(무인민원발급기 설치장소 500여 줄, 노숙인 숙박시설, 임시주거시설 현황 등)가 통째로 섞여 들어가 있던 걸 발견 → `manual/fix_contact_field.py`로 실제 연락처만 남기고 나머지는 참고사항으로 이동
  2. "일반매뉴얼" 키워드("소화기", "비상연락", "당직민원 등록" 등)가 너무 흔해서 실제 시민 민원 문장과 우연히 충돌하는 걸 5,624건 재검증 중 발견 → 키워드를 더 구체적인 표현으로 좁혀 수정, 재검증 결과 실제 민원과의 오매칭 0건 확인
  3. **되묻기(follow-up)가 근거불충분(저신뢰) 문서에도 잘못 발동하는 버그** — "가스가 폭발했어요"처럼 키워드("가스폭발")와 정확히 안 맞아 유사도 기반 "근거불충분"으로 판정된 문서인데도, 결과 항목의 `tier`가 "매뉴얼"이라는 이유만으로 마치 확정 답변인 것처럼 자신 있게 되물어버림 → `app/recommend.py`에서 키워드 정확매칭(`유사도 is None`)일 때만 되묻기가 뜨도록 수정
  4. 위 버그를 고치다 "가스폭발", "하천 기름유출" 항목이 자연스러운 구어체 표현("가스가 폭발했어요", "하천에 기름이 유출됐어요")과 안 맞아서 되묻기 자체가 거의 발동 안 하고 있던 것도 발견 → 키워드에 구어체 변형 추가

### 3단계 — 매뉴얼에 없는 것들을 2024~2026년 데이터로 통계화해서 추가 등록

- **완성도: 5개 유형 확정, 전체 민원의 17.3% 커버**
- 매뉴얼에 안 걸리는 과거 민원들을 클러스터링해서, 사람이 검토 후 5개 반복유형(가로등 고장 403건, 노점상 단속 85건, 불법 현수막 철거 100건, 쓰레기 무단투기 80건, 미성년자 주류판매 단속 56건)을 "참고사례"로 등록 완료(`analysis/cluster_complaints.py` + `curate_recurring_types.py`)
- 참고사례는 매뉴얼처럼 확정 답변이 아니라 "공식 대응 아님"이라고 항상 명시하며 제공
- 클러스터링 자체의 정확도가 낮아서(실루엣 점수 낮음), 폐기한 클러스터 중에 아직 못 찾은 반복유형이 더 있을 가능성 있음 — 필요하면 재검토 가능

### 전체 정확도 요약 (2024~2026년 실제 민원 5,624건 기준, `search/evaluate_engine.py` 검증)

| 근거수준 | 비율 | 1순위 부서 정확도 |
|---|---|---|
| 매뉴얼(1단계) | 43.2% | 88.6% |
| 참고사례(3단계) | 17.3% | 76.4% |
| 근거불충분 | 38.3% | 29.6% (낮은 게 정상 — 확신 없다는 신호) |
| 결과없음 | 1.2% | — |

("일반매뉴얼" tier는 이 표에서 빠져있음 — 민원 대응이 아니라 당직자 자기참고용 조회라서, 과거 민원 데이터로 정확도를 검증할 "정답 부서" 자체가 없음)

**즉, 전체 민원의 60.5%(매뉴얼+참고사례)는 시스템이 근거를 갖고 답변할 수 있고, 나머지 39.5%는 "확실하지 않다"고 정직하게 안내합니다.** 답변한 것들의 정확도(88.6%/76.4%)는 높은 편이라, "억지로 답하지 않는다"는 원칙과 "답할 땐 믿을 만하게 답한다"는 목표 둘 다 지켜지고 있다고 판단합니다.

## ⚠️ 반드시 지켜야 할 핵심 규칙 (진행하면서 놓치면 안 되는 것들)

1. **PDF 매뉴얼은 85페이지 전체 내용이 빠짐없이 들어가야 한다.** (완료) "상황→대응→부서→연락처" 형식의 케이스형 내용 28개(19개 민원처리 + 9개 재난유형별, `manual/situations.json`)에 이어, 케이스형이 아닌 나머지 8개 섹션도 `manual/parse_general_sections.py`로 추가 반영 완료(`manual/general_docs.json`):
   - 당직근무자 준수사항(p4~6), 재난상황 보고체계 개요(p7~15), 청사 보안 및 시건(p16~20),
     휴일 비상연락·비상발령 및 소집체계(p21~25), 재난상황 당직사령 개요 및 1-1 자연재난 조치요령(p26~34),
     재난관리책임기관 연락체계도(p48), 당직근무일지 작성 및 당직민원 등록(p49~51), 소화기 및 질식소화포 비치(p85)
   - 이 내용들은 민원 대응 케이스가 아니라 당직자 본인이 참고하는 내부 근무수칙이라, 검색 결과에서 `근거수준: "일반매뉴얼"`로 따로 구분해 제공(`manual/general_lookup.py` 키워드 매칭, `search/engine.py`에 통합)
   - **한계**: 청사 보안 및 시건(p16~20), 재난관리책임기관 연락체계도(p48)는 원래 도면·흐름도라서 텍스트로 뽑으면 줄글이 아니라 단어가 흩어진 형태로 나옴. "빠짐없이 반영"이라는 요구사항에 따라 원문 그대로 포함은 했으나, 사람이 읽기엔 PDF 원본을 직접 보는 게 나음
2. **근거 불충분 시 임의로 답변을 만들어내지 않는다** (명세서 핵심 조항). 확신 없으면 "모른다"고 솔직히 말하고 담당 부서 문의를 안내 — 매뉴얼 확정답/참고사례/근거불충분/결과없음 4단계 원칙 유지
3. **매뉴얼(공식) 우선순위가 참고사례(비공식, 과거 데이터 기반)보다 항상 위**. 참고사례는 "공식 대응 아님"을 항상 명시
4. **매뉴얼 항목 안에 세부 케이스가 섞여있으면 전체를 다 보여주지 말고 되물어서 좁힌다** (`search/followup.py`, 분기가 있는 10개 항목에 구현 완료). 선택지 어디에도 안 맞는 **예외 상황은 억지로 답하지 말고 담당 부서에 직접 문의**하도록 안내(모든 역질문에 공통 적용)
5. **검색 결과는 요약하지 말고 최대한 자세하게(원문 전체) 보여준다** — 앞부분 몇 줄만 보여주는 식으로 자르면 안 됨
6. **공개 GitHub 저장소이므로 개인정보 포함 파일은 절대 커밋 금지** — 원본 엑셀·PDF, `manual/situations.json`, `analysis/*.json`, `analysis/*.csv` 등은 `.gitignore`로 제외, 코드만 공개

## 0. 요구사항 명세서 핵심 요약

- **프로젝트명**: 당직 근무자를 위한 문서 기반 민원 검색 플랫폼
- **목적**: 당직 근무자가 민원 발생 시 당직 매뉴얼·기존 민원 목록을 근거로 필요한 정보를 신속히 검색하고, 반복 민원의 대응 방법을 확인
- **범위 (중요)**: 모든 민원·예외상황을 포괄적으로 처리하는 시스템이 **아님**. 우선순위는
  1. 매뉴얼 기반 신속 검색
  2. 반복 민원 유형 정리
  3. 기존 민원 목록으로 대응 내용 보충
  4. **문서 근거가 명확한 경우에만** 짧은 안내 제공
  5. 관련 문서·담당 부서·참고 내용 제공
- **핵심 원칙 (설계를 좌우하는 조항)**: 근거가 불충분하거나 관련 문서를 찾을 수 없으면 **임의로 답변을 생성하지 않고**, 정보가 부족하다는 사실을 그대로 안내한다.
- **데이터 2종과 위계**:
  - 당직 매뉴얼 = **공식 대응 절차·1순위 근거**
  - 3개년 당직 민원 목록 = **보조 자료** (반복 유형·유사 사례 파악용). 매뉴얼에 없는 내용은 공식 대응으로 단정하지 않고 "참고 사례"로만 사용
- **UI 필수 요소**: 검색창/결과 목록(관련 문서명·민원유형·관련문단·짧은안내·담당부서·참고사항·원문확인 버튼)/결과없음 안내문/근거불충분 안내문(문구 원문은 5절 참고)
- **관리 기능(신규 요구사항)**: 매뉴얼·민원목록 등록, 반복 민원 유형 및 대응 추가, 문서/민원 정보 수정, 오래되거나 잘못된 정보 삭제, 최신 상태 관리

## 1. 기존 접근과의 차이 — 왜 전면 수정인가

| 항목 | 기존(수정 전) 접근 | 명세서가 요구하는 접근 |
|---|---|---|
| 핵심 산출물 | 민원내용 → **담당부서**를 예측하는 지도학습 분류 모델 | 검색어 → **관련 문서(매뉴얼/과거민원)**를 찾아 근거와 함께 보여주는 검색 엔진 |
| 매뉴얼 밖 상황 처리 | ML 모델이 확률과 함께 부서를 "참고 예측"으로 제시 (`app/recommend.py`의 ML예측 분기) | 근거가 임계치 이상이 아니면 **"정보 부족" 안내만** — 확률적 추측을 답처럼 보여주면 안 됨 |
| 과거 민원 데이터의 역할 | 정답 라벨(`처리부서`)로 지도학습에 사용 | **참고 사례 검색 대상** (라벨 예측이 아니라 유사 사례 제시), 반복 유형 클러스터링 재료 |
| 정확도 지표 | Top-1/Top-3 accuracy, F1 | 검색 관련도, "근거 있음/없음" 판정의 정확성(정보 부족을 정보 부족이라고 맞게 말하는가) |

**결론**: 기존에 만든 매뉴얼 구조화·EDA·정규화 결과물은 그대로 재사용 가능하지만, 분류 모델과 `app/recommend.py`의 ML 예측 분기는 **검색/유사도 매칭 엔진으로 대체**해야 합니다(분류 모델 코드는 이후 삭제됨, 4절 참고). 4절에 파일별 유지/교체 여부를 정리했습니다.

## 2. 사용자 및 데이터

- **사용자**: 유성구청 당직 근무자 (내부 도구)
- **데이터**:

- **개인정보 처리**: 이 저장소는 public GitHub(`ssiyyeon/living-lab`)에 올라갑니다. 원본 엑셀·PDF와 그 내용을 그대로 담은 파생 파일(`manual/situations.json`, `analysis/action_categorized.csv`, `analysis/feedback_log.csv`, `analysis/recurring_complaint_types*.json`)은 `.gitignore`로 제외하고 코드만 공개합니다.

## 3. 데이터 분석 커리큘럼 (전면 개정)

### Phase 0 — 매뉴얼 구조화 (완료, 28개 상황으로 확장)

PDF의 "당직근무 민원처리 매뉴얼" 섹션(19개 상황)을 파싱해 `manual/situations.json`(부서·민원요지·처리방법·참고사항·담당자연락처·페이지)으로 구조화. 이 구조가 그대로 **검색엔진의 1순위 인덱스**가 됩니다.

**추가 발견 (85페이지 중 놓친 부분)**: "PDF 전체가 다 매뉴얼 아니냐"는 지적을 받고 다시 확인해보니, 실제로 앞부분(p33~47) "Ⅲ. 재난유형별 행동매뉴얼"에 대설(제설)·지하차도 침수·도로상 낙하물·화재·하천 기름유출·구제역/AI·가스폭발·산불·건축물 붕괴 총 9개 상황이 "가.근무사항+나.비상연락망" 형식으로 정리되어 있었는데, Phase 0을 처음 할 때 뒷부분(p52~) "당직근무 민원처리 매뉴얼" 섹션만 보고 이 부분을 통째로 빠뜨렸습니다. `manual/parse_disaster_manual.py`로 이 9개를 파싱해 추가 → **총 28개 상황**. (1-1 태풍·호우 개요와 사회재난 총론 페이지는 개별 민원 대응 절차라기보다 기관 내부 보고체계 위주라 제외)

이 발견의 실질적 효과: Phase 2에서 "매뉴얼에 없는 참고사례"로 분류했던 **제설 작업 요청·지하차도 침수·중앙분리대/가드레일 파손 3종이 사실은 이미 공식 매뉴얼에 있었음**이 드러나, 참고사례(비공식, 신뢰도 76%)에서 매뉴얼(공식, 신뢰도 89%)로 승격했습니다. 화재·하천기름유출은 부서가 조건부(피해 유형에 따라 분기)이거나 기존 키워드와 중복돼 자동 키워드는 의도적으로 안 붙였습니다(문서에는 있지만 자동매칭은 보수적으로 접근).

### Phase 1 — 민원 데이터 EDA (완료, 그대로 재사용)

6,835건 분석: 컬럼 구조(`민원내용`→`당직자조치내용`→`처리부서`), 부서 편중(상위10개 89.1%), 결측 17.7%, `당직자조치내용` 표기변형 1,985종. 이 결과는 이제 "분류 라벨 분포"가 아니라 **"검색 대상 문서 컬렉션의 특성"**으로 재해석됩니다 — 예: 부서 편중이 심하다는 건 반복 민원 유형(Phase 2)도 소수 유형에 집중될 가능성이 높다는 뜻.

### Phase 1.5 — `당직자조치내용` 정규화 (완료, 그대로 재사용)

1,985개 표기 변형 → 10개 조치유형으로 정규화(96.2% 커버). 검색 결과에 "과거엔 이렇게 조치했음"을 붙일 때 이 정규화된 조치유형을 사용.

### Phase 2 — 반복 민원 유형 클러스터링 (1차 완료, `analysis/cluster_complaints.py`)

**목적**: 매뉴얼(19개 상황)이 다루지 않는 민원 중, 실제로 자주 반복되는 유형을 데이터 기반으로 찾아 "참고 사례 카드"를 만든다.

- **대상**: 매뉴얼 규칙에 하나도 안 걸리는 민원만 클러스터링 (매뉴얼이 이미 답을 주는 건 다시 묶을 필요 없음)
- **방법**: `민원내용`을 TF-IDF(char+word)로 벡터화 → KMeans. k는 15/20/30/40/50 후보 중 실루엣 점수로 선택(k=50). 처리부서 라벨은 클러스터링에 쓰지 않고 결과 해석에만 사용(비지도 원칙 유지)
- **결과 품질(솔직하게)**: 실루엣 점수가 0.01 안팎으로 낮음 — 군집이 뚜렷하게 잘 갈리진 않음. 상위 클러스터 중 절반 정도는 "가로등 불이 안들어옴"(244건), "고양이/고라니 사체 처리", "노점상·불법주정차 단속"처럼 뚜렷한 주제로 잘 묶였지만, 나머지는 "~후 전화 요망" 같은 문체·서식 유사성으로 묶인 잡음성 클러스터임. **사람이 상위 클러스터를 검토해서 선별하는 과정이 필요** (전부 자동으로 신뢰할 수 없음)
- **클러스터링에서 바로 건진 매뉴얼 키워드 버그 3건 (즉시 수정 완료)**:
  1. "고양이 사체"/"고라니사체"(띄어쓰기 없음)가 기존 키워드("동물사체", "고라니 사체")와 표기 차이로 미매칭 → "사체" 계열 키워드 보강
  2. "고양이 구조요청"/"부상 고양이"가 "길고양이 구조"와 어순 차이로 미매칭 → 유기동물 항목에 키워드 추가
  3. "고라니 구조"/"까치 구조"가 "야생동물 구조"와 표현 차이로 미매칭 → 부상야생동물 항목에 키워드 추가
  4. (부수) "주정차 단속"/"주차 단속"처럼 "불법"이 안 붙은 단속 요청도 불법주정차 항목에 추가
  - 위 수정으로 **매뉴얼 매칭률 34.1% → 40.4%**로 개선
- **클러스터를 주제별로 병합해 정리한 "확정 반복 민원 유형"** (매뉴얼엔 없지만 자주 반복되는 것들, `analysis/curate_recurring_types.py`):

  | 반복 민원 유형 | 건수(대략) | 부서 | 근거수준 |
  |---|---|---|---|
  | 가로등 고장/불량 | ~403건 | 건설과 | 참고사례 (매뉴얼에 없음, 최대 규모 사각지대) |
  | 불법 현수막 철거 | ~100건 | 건축과 | 참고사례 |
  | 노점상 단속 | ~85건 | 건설과 | 참고사례 |
  | 쓰레기 무단투기(표현差) | ~80건 | 청소행정과 | 참고사례 (기존 키워드 있으나 표현 차이로 미매칭) |
  | 미성년자 주류판매 단속 | ~56건 | 위생과 | 참고사례 |

  나머지 클러스터는 "~후 전화 요망"류 문체 유사성으로 묶인 잡음이라 반복유형으로 확정하지 않고 폐기. (도로 침수/배수, 중앙분리대·가드레일 파손, 제설 작업 요청은 Phase 0에서 매뉴얼로 승격되어 이 목록에서 빠짐 — 위 참고)
- 원본 클러스터 출력: `analysis/recurring_complaint_types.json` (건수·대표키워드·주요부서·주요조치유형·예시 3건, `근거수준: "참고사례"` 명시). 실제 민원 원문 포함이라 `.gitignore` 등록, 공개 저장소에는 미포함
- 확정된 5개 유형이 Phase 3 검색 인덱스에 "참고사례" 계층으로 들어감 (매뉴얼 계층보다 후순위)

### Phase 3 — 검색/유사도 매칭 엔진 (완료, `search/engine.py`)

**목적**: 검색어/민원내용을 입력하면 매뉴얼(Phase 0) + 확정 반복유형 카드(Phase 2)를 대상으로 관련 문서를 찾는다. 지도학습 분류가 아니라 **정보 검색(IR)** 문제로 접근.

- 인덱스 대상: (1) 매뉴얼 19개 상황 (2) Phase 2에서 확정한 반복유형 8종 (`search/reference_cases.py`가 `analysis/recurring_complaint_types_curated.json`을 로드)
- 매칭 방법: TF-IDF(char+word) 코사인 유사도. 매뉴얼 문서는 처리방법 본문이 길어 핵심 키워드가 희석되는 문제가 있어, 민원요지·부서·키워드를 6번 반복해 제목에 가중치를 준 뒤 인덱싱(`_build_manual_docs`의 title-boost)
- 매뉴얼 히트가 항상 최우선, 반복유형 카드는 그 다음 순위 (명세서의 "매뉴얼 = 공식 근거, 민원목록 = 보조 자료" 위계 그대로 구현)
- 기존 `manual/rule_lookup.py`의 키워드 사전은 매뉴얼 문서 텍스트 구성에 그대로 재사용

### Phase 4 — 근거 판정 및 응답 규칙 (완료, `search/engine.py`의 `SearchEngine.search()`에 통합 구현)

**목적**: "근거 불충분 시 임의 답변 금지"를 실제 로직으로 구현. 유사도 점수에 임계치 3개를 둬서 4단계로 분기.

| 임계치 | 값 | 의미 |
|---|---|---|
| `MANUAL_THRESHOLD` | 0.12 | 이 이상이면 매뉴얼 확정 응답 |
| `REFERENCE_THRESHOLD` | 0.10 | 매뉴얼 미달 시, 이 이상이면 참고사례 응답 |
| `MIN_RELEVANCE` | 0.03 | 이 미만이면 "결과없음" (그 사이는 "근거불충분") |

| 판정(`근거수준`) | 응답 |
|---|---|
| `매뉴얼` | 관련 문서명·민원유형·관련 문단(처리방법 발췌, 창작 아님)·담당부서·참고사항 |
| `참고사례` | "매뉴얼에 등재되지 않은 상황"임을 명시하고 과거 유사 건수·주요 처리부서만 제공 (공식 대응 아님) |
| `근거불충분` | 명세서 문구 + 임계치 미달이지만 가장 가까운 후보 문서 목록 |
| `결과없음` | 명세서 문구만, 결과 목록은 비움 |

- 결과 없음: *"관련 문서에서 해당 민원에 대한 명확한 내용을 찾지 못했습니다. 검색어를 변경하거나 관련 담당 부서에 확인해 주세요."*
- 근거 불충분: *"검색된 문서만으로는 대응 방법을 명확하게 안내하기 어렵습니다. 아래 관련 문서를 확인하거나 담당 부서에 문의해 주세요."*

**전체 데이터(5,624건)로 검증 완료 (`search/evaluate_engine.py`)** — 손으로 고른 15개 쿼리만으로는 못 보는 문제를 두 가지 발견하고 고쳤다.

1. **회귀 발견**: 순수 유사도 임계치만 쓰면, 기존 키워드 규칙이 명백히 매칭하는 2,274건 중 294건(13%)이 처리방법 본문 길이 때문에 임계치를 못 넘겨 "근거불충분"으로 격하됨 → **키워드 매칭은 유사도 계산 없이 무조건 매뉴얼 tier로 확정**하도록 수정 (`search/engine.py`의 `match_manual` 우선 처리)
2. **더 심각한 발견**: 키워드는 없지만 유사도만으로 "매뉴얼"이라 판정한 725건을 실제 처리부서와 대조하니 **일치율 48.7%**(거의 반반, 못 믿을 수준)였던 반면 키워드 매칭 건은 89.0%였음 → 유사도만으로 "공식 매뉴얼 근거"를 확정하는 건 명세서의 "근거 불충분 시 임의 답변 금지" 원칙 위반이라 판단, **이 경로를 제거**. 유사도만 있는 경우는 최대 "참고사례"까지만 인정

**수정 후 검증 결과, 그리고 Phase 0 매뉴얼 확장(28개 상황) 반영 후 최종 결과 (전체 5,624건)**

| 근거수준 | 비율 | 1순위 부서 일치율 |
|---|---|---|
| 매뉴얼 | 43.2% (2,427건, 키워드 매칭과 정확히 일치) | 88.6% |
| 참고사례 | 17.3% (974건) | 76.4% |
| 근거불충분 | 38.3% (2,153건) | 29.6% (낮은 게 정상 — 신뢰도 낮음을 스스로 보여줌) |
| 결과없음 | 1.2% (70건) | — |

신뢰도 순서(매뉴얼 89% > 참고사례 76% > 근거불충분 30%)가 상식과 맞게 나와, 근거수준 분류 자체가 실제로 신뢰도를 반영하고 있음을 확인. 매뉴얼 확장 전(40.4%)보다 커버리지가 늘면서도(43.2%) 정확도는 그대로 유지됨(89%대). `app/recommend.py`가 이제 이 엔진의 얇은 래퍼로 교체되어, 기존 분류 모델은 더 이상 쓰이지 않아 저장소에서 삭제했음(4절 참고, git 이력에는 남아있음).

**한계(솔직하게)**: 참고사례 검증은 그 카드 자체가 같은 데이터에서 만들어졌으므로 다소 낙관적일 수 있음(데이터 누수). 매뉴얼 tier 89%도 100%는 아닌데, 일부는 "도로 위 쓰레기는 건설과" 같은 부서 간 교차 관례 때문으로 보임 — 완전한 오류라기보다 매뉴얼 자체의 실제 운영상 예외로 추정.

### Phase 5 — 사용자 인터페이스 (명세서 화면 요구사항 반영)

- **메인 검색 화면**: 시스템명, 검색창, 검색 버튼, 검색어 입력 예시, 결과 표시 영역
- **검색 결과 화면**: 관련 문서명 / 민원 유형 / 관련 문단 / 짧은 안내 / 담당 부서 / 참고 사항 / 원문 확인 버튼
- **시나리오 대응**:
  - 일반 검색: 결과 목록 → 선택 → 상세(문단·대응·부서·안내) → 원문 확인
  - 복수 문서(중의적 검색어): 하나로 단정하지 않고 민원 유형별로 구분해 목록 제공
  - 결과 없음: 위 4절의 "결과 없음" 문구
- 이 부분은 웹 개발 협업 필요 (Phase 3~4가 API로 노출되면 그 위에 UI를 얹는 구조)

### Phase 6 — 문서/민원 정보 관리 기능 (신규, 미착수)

명세서의 "문서 및 민원 정보 관리" 요구사항 — 지금까지 전혀 다루지 않은 부분.

- 당직 매뉴얼 등록 / 기존 민원 목록 등록
- 반복 민원 유형 및 대응 내용 추가 (Phase 2 클러스터 결과를 관리자가 검토 후 수동 승인·추가하는 흐름 필요)
- 문서·민원 정보 수정, 오래되거나 잘못된 정보 삭제
- 담당 부서·참고 정보 수정, 문서 최신 상태 확인·관리
- 이전 계획에 있던 "실시간 피드백 루프"(현재 `app/feedback.py`)가 이 관리 기능의 입력 소스 중 하나로 재편입 — 피드백으로 쌓인 새 사례를 관리자가 검토해 매뉴얼/반복유형에 반영하는 흐름으로 연결

### Phase 7 — 검증

- 당직 근무자 대상 실사용 테스트: 검색 소요시간, "근거 없음" 안내가 실제로 적절한 시점에 나오는지, 잘못된 부서/문서를 연결하지 않는지 확인

## 5. 실행 방법

```bash
pip install -r requirements.txt   # 프로젝트 루트의 .venv 사용 권장

# Phase 2: 반복 민원 유형 클러스터링 + 큐레이션 (검색엔진이 참조하는 참고사례 데이터 생성)
python3 analysis/cluster_complaints.py
python3 analysis/curate_recurring_types.py

# 검색 함수 CLI 테스트 (Phase 3~4, search/engine.py)
python3 app/recommend.py "궁동에서 유기견을 발견했어요"
python3 search/engine.py   # 데모 쿼리 여러 개로 근거수준 확인

# 전체 데이터로 임계치·근거수준 신뢰도 검증
python3 search/evaluate_engine.py

# 스모크 테스트
python3 tests/test_smoke.py
```

과거 분류 모델 스크립트(`model/` 폴더)는 검색 흐름 전환 후 아무 데서도 쓰이지 않아 저장소에서 삭제했다(4절 참고, git 이력에는 남아있음).
