# 유성구청 리빙랩 — 민원 안내 간편화 프로젝트

## 1. 프로젝트 배경 및 목적

- 현재: 민원(특히 당직 시간대 상황별 민원)이 들어오면 담당자가 `당직 근무요령 및 상황별 매뉴얼` PDF를 직접 찾아보며 대응
- 문제: 매뉴얼이 두껍고(PDF, 다수 페이지) 상황별로 흩어져 있어 필요한 항목을 빨리 찾기 어려움
- 목표: 매뉴얼 내용을 구조화하고, 실제 민원 데이터를 반영해 **담당자가 빠르게 답을 찾을 수 있는 웹사이트**를 제공
- 즉, 이 프로젝트는 "새 지식을 만드는 것"이 아니라 **이미 존재하는 매뉴얼 지식에 대한 접근성을 높이는 것**이 핵심

## 2. 사용자 및 데이터 확정

- **사용자**: 시청(유성구청) **직원** — 당직/민원 담당자가 사용하는 내부 도구
- **보유 자료**:
  - `2. ★(유성구) 당직 근무요령 및 상황별 매뉴얼_26. 5..pdf` — 상황별 대응 매뉴얼 원본
  - `당직민원 목록(2024/2025/2026)_검수완료.xlsx` — 2024.1.1~2026.5.31 실제 당직 민원 이력 (총 6,835건)
- **개인정보 처리**: 이 저장소는 public GitHub에 올라갑니다. 원본 엑셀·PDF에는 민원인 정보와 직원 개인 휴대폰번호가 포함되어 있어, `.gitignore`로 원본 데이터와 그걸 그대로 담고 있는 파생 파일(`manual/situations.json`, `analysis/action_categorized.csv`, `analysis/feedback_log.csv`, `model/artifacts/`)을 제외했습니다. 코드만 공개되며, 데이터는 로컬에만 보관됩니다.

## 3. 전체 진행 순서 (Phase)

### Phase 0 — 매뉴얼 구조화 (완료)

PDF의 "당직근무 민원처리 매뉴얼" 섹션(목차 기준 19개 상황)을 파싱해 `manual/situations.json`으로 구조화했습니다.
- 각 항목: `부서 | 민원요지 | 처리방법 | 참고사항 | 담당자연락처 | 페이지`
- `manual/rule_lookup.py`: 상황별 키워드(예: "유기동물"→지역산업과, "포트홀"→건설과, "아동학대"→아동복지과) 사전 및 매칭 함수
- 이 규칙은 **과거 민원 건수와 무관하게** 항상 동작 — 희귀 부서 문제의 핵심 대안 (Phase 3.5 참고)

### Phase 1 — 민원 데이터 EDA (완료)

`당직민원 목록(2024~2026)` 3개 파일, 총 6,835건 분석 결과:

- **컬럼 구조**: `민원내용`(자유텍스트, 평균 58자) → `당직자조치내용`(조치, 자유텍스트) → `처리부서`(이첩된 담당부서)
- **`처리부서`가 사실상 라벨**: 73개 부서가 등장하지만 매우 편중됨
  - 상위 5개 부서(건설과·주차관리과·청소행정과·푸른환경과·지역산업과)가 라벨된 민원의 **71.4%**
  - 상위 10개 부서가 **89.1%** 커버 → 실질적으로 10~15개 클래스 분류 문제
- **결측**: `처리부서` 17.7%(1,211건) 결측 — 대부분 "부서 미배정" 상태와 일치, 학습 시 제외
- **품질 이슈**: `당직자조치내용`은 "담당부서 이첩"의 표기 변형(띄어쓰기·오탈자)으로 unique값이 1,985개까지 흩어짐 → 정규화 시 10여 개 패턴으로 수렴
- **스키마 드리프트**: 2026년 파일부터 `당직구분`(숙직/일직), `처리상태` 컬럼 추가 (2024/2025엔 없음)

### Phase 2 — 방식 결정: "모델이 꼭 필요한가?" (결론: 가벼운 분류 모델 채택)

민원 유형이 카테고리(부서)로 이미 정리되고 있고, 클래스가 10~15개 수준으로 좁혀지는 게 확인되어 **딥러닝 없이 TF-IDF + 로지스틱회귀 같은 경량 분류 모델**로 충분하다고 판단했습니다. (라벨이 거의 없거나 클래스가 수백 개였다면 규칙 기반/유사도 검색부터 시작하는 게 맞았을 것 — 지금 데이터는 분류 모델을 정당화할 만큼 구조가 명확함)

### Phase 3 — 프로토타입: 민원내용 → 담당부서 분류 (완료, 베이스라인)

`model/baseline_dept_classifier.py` — TF-IDF(char n-gram) + Logistic Regression, 건수 10 미만 부서는 "기타"로 그룹핑(32개 클래스), 80/20 split.

| 지표 | 결과 |
|---|---|
| Top-1 정확도 | 78% (weighted F1 0.78) |
| Top-3 정확도 | 89.5% |
| 주요 부서 F1 | 건설과 0.85 / 주차관리과 0.90 / 청소행정과 0.91 / 지역산업과 0.84 |
| 약점 | 건수 적은 소수 부서(동 단위 등)는 F1 낮음 — 데이터 부족이 원인 |

**결론**: 담당자가 민원 텍스트를 입력하면 상위 3개 후보 부서를 보여주는 것만으로도 실무 활용 가능한 수준.

### Phase 3.5 — 모델 고도화 + 매뉴얼 규칙 하이브리드 (완료, 결과 정리)

특성 강화(char+word TF-IDF 결합) 및 매뉴얼 키워드 규칙과 ML을 결합한 하이브리드 라우터(`model/hybrid_router.py`)를 시도했습니다.

- 흔한 부서(상위 10개) 정확도: 기존과 거의 동일 (84%대) — 피처/모델을 바꿔도 크게 개선되지 않음. 이미 텍스트만으로 뽑아낼 수 있는 정보의 한계에 근접했다고 판단
- **핵심 발견**: 과거 건수가 4건 이하인 "극희귀 부서"는 ML이 원천적으로 학습 불가 (샘플 자체가 없음). 이 중 일부(아동학대→아동복지과, 노숙인→생활보장과, 유기동물→지역산업과 등)는 매뉴얼에 등재되어 있어 **키워드 규칙으로 커버 가능**
- 반면 실제 테스트에서 걸린 극희귀 케이스 10건을 까보니, 상당수가 철도건설국·한국도로공사·대전지방경찰청·기획재정부처럼 **애초에 유성구청 매뉴얼이 다루지 않는 외부기관 이관 건**이었음 → 이런 건은 규칙도 모델도 원천적으로 못 맞히는 게 정상 (도메인 밖의 예외 상황)
- **결론**: 흔한 민원은 지금 모델로 충분하고, 매뉴얼에 있는 상황은 규칙으로 보완 가능하지만, 매뉴얼에도 없는 완전히 새로운 예외 상황은 데이터/규칙이 아니라 **사람이 기록해서 축적하는 방식**(Phase 6 참고)으로만 해결 가능

#### 매뉴얼 커버리지 현황 (실사용 테스트로 드러난 한계)

실제 사용 테스트 중 "노은동 불법 현수막 철거"처럼 매뉴얼에 전혀 없는 입력이 계속 ML로만 처리되는 걸 확인하고, 전체 데이터 기준으로 커버리지를 다시 측정했습니다.

- 전체 라벨링된 민원(5,624건) 중 **매뉴얼 규칙에 매칭되는 건 34.1%뿐**, 나머지 65.9%는 ML 참고 예측으로 처리됨
- 이유: 원본 PDF의 "당직근무 민원처리 매뉴얼" 섹션 자체가 **19개 상황·11개 부서만** 다루는 좁은 문서라서 (전체 73개 부서 중 일부만 커버) — 버그가 아니라 원본 문서의 태생적 한계
- "현수막"은 85페이지 전체를 전수 검색해도 실제로 존재하지 않음(확인 완료). 다만 이 케이스는 183건(전체의 2.7%)이나 있었고 그중 76%가 건축과로 처리되어, ML이 매뉴얼 없이도 건축과를 85% 신뢰도로 정확히 맞힘 → 매뉴얼 미등재라고 해서 무조건 못 믿을 예측은 아님

**매뉴얼 미등재 건수 기준 우선순위 (사각지대 후보)**

| 부서 | 미매칭 건수 | 상태 |
|---|---|---|
| 건설과 | 1,056 | 일부만 커버 (포트홀/싱크홀 외 다른 상황 빠짐) |
| 청소행정과 | 525 | 일부만 커버 (재활용/쓰레기/불법투기 외 빠짐) |
| 주차관리과 | 387 | 일부만 커버 (불법주정차 외 빠짐) |
| 푸른환경과 | 218 | 일부만 커버 |
| **건축과** | 211 | **부서 자체가 매뉴얼에 전혀 없음** (현수막이 주 사유) |
| **공원과** | 202 | **부서 자체가 매뉴얼에 전혀 없음** |
| 지역산업과 | 170 | 일부만 커버 (유기동물 외 빠짐) |
| 교통정책과 | 167 | 일부만 커버 (마을버스 외 빠짐) |
| **재난안전과** | 135 | **부서 자체가 매뉴얼에 전혀 없음** |
| 녹지산림과 | 92 | 일부만 커버 (가로수 외 빠짐) |

**결론 및 다음 액션**: 매뉴얼 우선 설계 자체는 유효하지만(34%는 확실한 답 제공), 실제 활용도를 높이려면 매뉴얼 자체의 확장이 필요합니다. 다만 공식 대응절차·담당자 연락처는 제가 임의로 만들 수 없고 각 부서 실무자 확인이 필요하므로, **건축과·공원과·재난안전과처럼 부서 전체가 빠진 곳부터 유성구청에 매뉴얼 추가를 건의**하는 게 우선순위입니다.

### Phase 4 — 웹사이트 구현

**백엔드 로직은 준비 완료.** `app/recommend.py`의 `recommend(text)` 함수 하나로 다음이 다 됩니다.

**설계 원칙: 매뉴얼이 항상 1순위.** 직원은 실제로 매뉴얼을 근거로 대응하기 때문에, 매뉴얼에 등재된 상황이면 그 결과만(처리방법·참고사항·담당자 연락처 포함) 반환하고, 낮은 확률의 ML 추측을 섞어서 헷갈리게 하지 않습니다. ML 예측은 **매뉴얼에 아예 없는 새로운 상황일 때만** "참고용, 담당자 확인 필요"로 명확히 구분해서 보여줍니다.

- `model/train_and_save.py`로 학습한 모델(`model/artifacts/`)을 로드 (매 요청마다 재학습 안 함)
- 입력 민원 텍스트 → 매뉴얼 규칙(`manual/rule_lookup.py`) 매칭 시도
  - 매칭되면: `{"출처": "매뉴얼", "결과": [...]}` — 해당 매뉴얼 상황의 처리방법을 그대로 반환
  - 매칭 안 되면: `{"출처": "ML예측(매뉴얼 미등재)", "결과": [...]}` — 과거 데이터 기반 참고용 부서 예측 (신뢰도만 제공, 대응절차 없음)

남은 건 웹 개발 협업자가 `recommend()`를 API 엔드포인트로 감싸고(Flask/FastAPI 등), 프론트에서 검색창 + 결과 카드 UI를 붙이는 것.

### Phase 5 — 검증 및 피드백
- 실제 당직 담당자 대상 테스트 → "찾는 데 걸리는 시간"이 실제로 줄었는지 확인
- 검색이 안 되거나 틀린 항목을 추천하는 케이스 수집 → 매뉴얼 구조화/검색 로직 개선에 반영

### Phase 6 — 실시간 피드백 루프 (스켈레톤 구현 완료, 웹 UI 연결은 아직)

Phase 3.5에서 확인했듯, 매뉴얼에도 없는 완전히 새로운 상황(외부기관 이관 등)은 데이터나 규칙으로 미리 못 잡습니다. 이런 부분은 **실사용 중 피드백을 쌓아서 보완**하는 방식이 현실적인 대안입니다.

- **아이디어**: 담당자가 민원을 등록하고, 시스템이 추천한 부서/대응절차로 실제 해결이 됐다면 "이렇게 해결됐다"를 짧게 남길 수 있는 피드백 입력을 웹사이트에 추가
  - 추천이 맞았으면: 원클릭으로 "맞음" 확인 → 해당 (민원내용, 부서) 쌍이 새 학습 데이터로 누적
  - 추천이 틀렸거나 추천 자체가 없었으면(매뉴얼에도 없는 새 상황): 실제 처리 부서·방법을 직접 입력 → 이게 쌓이면 매뉴얼에 없는 새 상황을 발견하는 신호가 됨
- **왜 필요한가**: 지금 데이터로는 도저히 못 푸는 "극희귀 부서/새로운 상황" 문제의 근본 원인이 데이터 부족이었는데, 이 피드백이 정확히 그 데이터를 가장 필요한 지점(모델이 자주 틀리거나 아예 다루지 못하는 지점)에서 자동으로 채워줌 (일종의 능동학습)
- **구현 현황**: `app/feedback.py`에 `save_feedback()` / `load_feedback_log()`를 추가해 백엔드 로직의 최소 형태를 먼저 만들어 뒀습니다. 담당자가 `recommend()` 결과에 대해 맞음/틀림(+실제부서)을 남기면 `analysis/feedback_log.csv`에 append-only로 쌓입니다.
  - 아직 안 된 것: 웹 UI에서 이 함수를 호출하는 버튼/폼, 그리고 쌓인 로그를 `model/train_and_save.py` 재학습에 자동 반영하는 파이프라인. 지금은 로그를 쌓기만 하고, 재학습 반영은 사람이 주기적으로 검토 후 수동으로 진행하는 걸 전제로 함.
  - **구현 시 고려할 점**: 최소한의 입력(예: 부서 선택 드롭다운 + 한 줄 메모)으로 부담 없이 남길 수 있게 설계, 반복적으로 등장하는 새 상황은 매뉴얼 담당자에게 알려 정식 매뉴얼 업데이트로 이어지게 연결

## 4. 실행 방법

```bash
pip install -r requirements.txt

# 모델 학습(model/artifacts/에 저장, 데이터나 코드가 바뀌면 재실행)
python3 model/train_and_save.py

# 추천 함수 CLI로 테스트
python3 app/recommend.py "궁동에서 유기견을 발견했어요"

# 스모크 테스트 (pytest 불필요)
python3 tests/test_smoke.py
```
