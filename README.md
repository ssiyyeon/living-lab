# 당직 근무자를 위한 문서 기반 민원 검색 플랫폼 (유성구청 리빙랩)

> 이 README는 공식 **요구사항 명세서**를 기준으로 전면 개정되었습니다. 이전 버전은 "민원내용 → 담당부서 분류 모델"을 목표로 진행했지만, 명세서 확인 결과 이 프로젝트의 정체는 **분류/예측 시스템이 아니라 문서 기반 검색·근거 제공 플랫폼**입니다. 아래 0~1절에 그 차이를 정리하고, 3절부터 새 커리큘럼을 제시합니다.

## 0. 요구사항 명세서 핵심 요약

- **프로젝트명**: 당직 근무자를 위한 문서 기반 민원 검색 플랫폼
- **목적**: 당직 근무자가 민원 발생 시 당직 매뉴얼·기존 민원 목록을 근거로 필요한 정보를 신속히 검색하고, 반복 민원의 대응 방법을 확인
- **범위 (중요)**: 모든 민원·예외상황을 포괄적으로 처리하는 시스템이 **아님**. 우선순위는
  1. 매뉴얼 기반 신속 검색
  2. 반복 민원 유형 정리
  3. 기존 민원 목록으로 대응 내용 보충
  4. **문서 근거가 명확한 경우에만** 짧은 안내 제공
  5. 관련 문서·담당 부서·참고 내용 제공
- **핵심 원칙 (설계를 좌우하는 조항)**: 근거가 불충분하거나 관련 문서를 찾을 수 없으면 **임의로 답변을 생성하지 않고**, 정보가 부족하다는 사실을 그대로 안내한다.
- **데이터 2종과 위계**:
  - 당직 매뉴얼 = **공식 대응 절차·1순위 근거**
  - 3개년 당직 민원 목록 = **보조 자료** (반복 유형·유사 사례 파악용). 매뉴얼에 없는 내용은 공식 대응으로 단정하지 않고 "참고 사례"로만 사용
- **UI 필수 요소**: 검색창/결과 목록(관련 문서명·민원유형·관련문단·짧은안내·담당부서·참고사항·원문확인 버튼)/결과없음 안내문/근거불충분 안내문(문구 원문은 5절 참고)
- **관리 기능(신규 요구사항)**: 매뉴얼·민원목록 등록, 반복 민원 유형 및 대응 추가, 문서/민원 정보 수정, 오래되거나 잘못된 정보 삭제, 최신 상태 관리

## 1. 기존 접근과의 차이 — 왜 전면 수정인가

| 항목 | 기존(수정 전) 접근 | 명세서가 요구하는 접근 |
|---|---|---|
| 핵심 산출물 | 민원내용 → **담당부서**를 예측하는 지도학습 분류 모델 | 검색어 → **관련 문서(매뉴얼/과거민원)**를 찾아 근거와 함께 보여주는 검색 엔진 |
| 매뉴얼 밖 상황 처리 | ML 모델이 확률과 함께 부서를 "참고 예측"으로 제시 (`app/recommend.py`의 ML예측 분기) | 근거가 임계치 이상이 아니면 **"정보 부족" 안내만** — 확률적 추측을 답처럼 보여주면 안 됨 |
| 과거 민원 데이터의 역할 | 정답 라벨(`처리부서`)로 지도학습에 사용 | **참고 사례 검색 대상** (라벨 예측이 아니라 유사 사례 제시), 반복 유형 클러스터링 재료 |
| 정확도 지표 | Top-1/Top-3 accuracy, F1 | 검색 관련도, "근거 있음/없음" 판정의 정확성(정보 부족을 정보 부족이라고 맞게 말하는가) |

**결론**: 기존에 만든 매뉴얼 구조화·EDA·정규화 결과물은 그대로 재사용 가능하지만, 분류 모델(`model/baseline_dept_classifier.py`, `dept_classifier_v2.py`, `hybrid_router.py`, `train_and_save.py`)과 `app/recommend.py`의 ML 예측 분기는 **검색/유사도 매칭 엔진으로 대체**해야 합니다. 4절에 파일별 유지/교체 여부를 정리했습니다.

## 2. 사용자 및 데이터

- **사용자**: 유성구청 당직 근무자 (내부 도구)
- **데이터**:
  - `당직 근무요령 및 상황별 매뉴얼` PDF — 1순위 근거 문서
  - `당직민원 목록(2024~2026)` 엑셀 3종, 총 6,835건 — 보조 자료(참고 사례·반복유형 재료)
- **개인정보 처리**: 이 저장소는 public GitHub(`ssiyyeon/living-lab`)에 올라갑니다. 원본 엑셀·PDF와 그 내용을 그대로 담은 파생 파일(`manual/situations.json`, `analysis/action_categorized.csv`, `analysis/feedback_log.csv`, `model/artifacts/`)은 `.gitignore`로 제외하고 코드만 공개합니다.

## 3. 데이터 분석 커리큘럼 (전면 개정)

### Phase 0 — 매뉴얼 구조화 (완료, 그대로 재사용)

PDF의 "당직근무 민원처리 매뉴얼" 섹션(19개 상황)을 파싱해 `manual/situations.json`(부서·민원요지·처리방법·참고사항·담당자연락처·페이지)으로 구조화. 이 구조가 그대로 **검색엔진의 1순위 인덱스**가 됩니다.

### Phase 1 — 민원 데이터 EDA (완료, 그대로 재사용)

6,835건 분석: 컬럼 구조(`민원내용`→`당직자조치내용`→`처리부서`), 부서 편중(상위10개 89.1%), 결측 17.7%, `당직자조치내용` 표기변형 1,985종. 이 결과는 이제 "분류 라벨 분포"가 아니라 **"검색 대상 문서 컬렉션의 특성"**으로 재해석됩니다 — 예: 부서 편중이 심하다는 건 반복 민원 유형(Phase 2)도 소수 유형에 집중될 가능성이 높다는 뜻.

### Phase 1.5 — `당직자조치내용` 정규화 (완료, 그대로 재사용)

1,985개 표기 변형 → 10개 조치유형으로 정규화(96.2% 커버). 검색 결과에 "과거엔 이렇게 조치했음"을 붙일 때 이 정규화된 조치유형을 사용.

### Phase 2 — 반복 민원 유형 클러스터링 (1차 완료, `analysis/cluster_complaints.py`)

**목적**: 매뉴얼(19개 상황)이 다루지 않는 민원 중, 실제로 자주 반복되는 유형을 데이터 기반으로 찾아 "참고 사례 카드"를 만든다.

- **대상**: 매뉴얼 규칙에 하나도 안 걸리는 민원만 클러스터링 (매뉴얼이 이미 답을 주는 건 다시 묶을 필요 없음)
- **방법**: `민원내용`을 TF-IDF(char+word)로 벡터화 → KMeans. k는 15/20/30/40/50 후보 중 실루엣 점수로 선택(k=50). 처리부서 라벨은 클러스터링에 쓰지 않고 결과 해석에만 사용(비지도 원칙 유지)
- **결과 품질(솔직하게)**: 실루엣 점수가 0.01 안팎으로 낮음 — 군집이 뚜렷하게 잘 갈리진 않음. 상위 클러스터 중 절반 정도는 "가로등 불이 안들어옴"(244건), "고양이/고라니 사체 처리", "노점상·불법주정차 단속"처럼 뚜렷한 주제로 잘 묶였지만, 나머지는 "~후 전화 요망" 같은 문체·서식 유사성으로 묶인 잡음성 클러스터임. **사람이 상위 클러스터를 검토해서 선별하는 과정이 필요** (전부 자동으로 신뢰할 수 없음)
- **클러스터링에서 바로 건진 실익 하나**: "고양이 사체", "고라니사체"(띄어쓰기 없음)가 기존 매뉴얼 키워드("동물사체", "고라니 사체")와 띄어쓰기 차이로 매칭이 안 되고 있던 걸 발견 → `manual/rule_lookup.py`에 키워드 추가로 즉시 수정, 매뉴얼 매칭률 34.1% → **38.7%**로 개선 (219건 회수)
- **새로 확인된 진짜 사각지대**: "가로등 불이 안들어옴/전부 꺼짐" 244건 — 매뉴얼 85페이지 전체에 없음(확인 완료), 건설과가 86%로 처리. 건축과·공원과·재난안전과에 이은 또 다른 매뉴얼 확장 후보
- 출력: `analysis/recurring_complaint_types.json` (클러스터별 건수·대표키워드·주요부서·주요조치유형·예시 3건, `근거수준: "참고사례"`로 명시). 실제 민원 원문을 포함하므로 `.gitignore`에 등록, 공개 저장소에는 올리지 않음
- **다음 단계**: 상위 클러스터를 사람이 검토해 "반복 민원 유형" 카드로 확정하고, 잡음성 클러스터는 폐기 — 확정된 카드가 Phase 3 검색 인덱스에 "참고사례" 계층으로 들어감

### Phase 3 — 검색/유사도 매칭 엔진 (신규, 기존 분류모델 대체)

**목적**: 검색어/민원내용을 입력하면 매뉴얼(Phase 0) + 반복유형 카드(Phase 2)를 대상으로 관련 문서를 찾는다. 지도학습 분류가 아니라 **정보 검색(IR)** 문제로 접근.

- 인덱스 대상: (1) 매뉴얼 19개 상황 (2) Phase 2 클러스터 대표 사례 (3) 필요시 개별 과거 민원 원문(유사 사례 확인용)
- 매칭 방법: TF-IDF/BM25 유사도부터 시작 (딥러닝 임베딩은 필요성이 확인된 뒤 검토 — 기존 프로젝트에서 "데이터 규모 대비 가벼운 모델로 충분"이었던 판단은 유지)
- 매뉴얼 히트가 항상 최우선, 클러스터/과거사례는 그 다음 순위 (명세서의 "매뉴얼 = 공식 근거, 민원목록 = 보조 자료" 위계 그대로 반영)
- 기존 `manual/rule_lookup.py`의 키워드 사전은 그대로 1차 필터로 재사용 가능

### Phase 4 — 근거 판정 및 응답 규칙 (신규, 명세서 핵심 조항 구현)

**목적**: "근거 불충분 시 임의 답변 금지"를 실제 로직으로 구현. 유사도 점수에 임계치를 둬서 3단계로 분기.

| 상황 | 판정 | 응답 |
|---|---|---|
| 매뉴얼 키워드/유사도 강한 매칭 | 근거 명확 | 관련 문서명·관련 문단·짧은 안내(추출 기반, 새로 창작 안 함)·담당부서·참고사항·원문 |
| 매뉴얼엔 없지만 Phase2 클러스터/과거사례 유사도가 임계치 이상 | 근거 약함(참고용) | "참고 사례" 라벨을 명확히 붙여 제공, 확정 안내문 대신 사례 나열 |
| 임계치 미만 / 관련 문서 없음 | 근거 없음 | 명세서 문구 그대로 출력 (아래) |

- 결과 없음: *"관련 문서에서 해당 민원에 대한 명확한 내용을 찾지 못했습니다. 검색어를 변경하거나 관련 담당 부서에 확인해 주세요."*
- 근거 불충분: *"검색된 문서만으로는 대응 방법을 명확하게 안내하기 어렵습니다. 아래 관련 문서를 확인하거나 담당 부서에 문의해 주세요."*

**주의**: "짧은 안내"는 검색된 문서 문장을 그대로 추출/요약하는 수준이어야 하며, 문서에 없는 내용을 생성형으로 지어내면 안 됨(명세서 원칙과 정면 충돌).

### Phase 5 — 사용자 인터페이스 (명세서 화면 요구사항 반영)

- **메인 검색 화면**: 시스템명, 검색창, 검색 버튼, 검색어 입력 예시, 결과 표시 영역
- **검색 결과 화면**: 관련 문서명 / 민원 유형 / 관련 문단 / 짧은 안내 / 담당 부서 / 참고 사항 / 원문 확인 버튼
- **시나리오 대응**:
  - 일반 검색: 결과 목록 → 선택 → 상세(문단·대응·부서·안내) → 원문 확인
  - 복수 문서(중의적 검색어): 하나로 단정하지 않고 민원 유형별로 구분해 목록 제공
  - 결과 없음: 위 4절의 "결과 없음" 문구
- 이 부분은 웹 개발 협업 필요 (Phase 3~4가 API로 노출되면 그 위에 UI를 얹는 구조)

### Phase 6 — 문서/민원 정보 관리 기능 (신규, 미착수)

명세서의 "문서 및 민원 정보 관리" 요구사항 — 지금까지 전혀 다루지 않은 부분.

- 당직 매뉴얼 등록 / 기존 민원 목록 등록
- 반복 민원 유형 및 대응 내용 추가 (Phase 2 클러스터 결과를 관리자가 검토 후 수동 승인·추가하는 흐름 필요)
- 문서·민원 정보 수정, 오래되거나 잘못된 정보 삭제
- 담당 부서·참고 정보 수정, 문서 최신 상태 확인·관리
- 이전 계획에 있던 "실시간 피드백 루프"(현재 `app/feedback.py`)가 이 관리 기능의 입력 소스 중 하나로 재편입 — 피드백으로 쌓인 새 사례를 관리자가 검토해 매뉴얼/반복유형에 반영하는 흐름으로 연결

### Phase 7 — 검증

- 당직 근무자 대상 실사용 테스트: 검색 소요시간, "근거 없음" 안내가 실제로 적절한 시점에 나오는지, 잘못된 부서/문서를 연결하지 않는지 확인
